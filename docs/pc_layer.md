# PC layer: hook spec for libNOVA.so

Read-only analysis of the arm64 `libNOVA.so` (IDA). Addresses are image-relative virtual addresses (add the guest load base). Every function listed is a real function at its address; callers reach it through a PLT stub (`.`-prefixed, `0x89xxxx`) and a GOT slot (`<name>_ptr`, `0x28xxxxx`), so patching the real entry catches all callers. "C" = confirmed by decompilation, "I" = inferred.

Threading rule: run all injections on the guest game thread (`glf::App::Impl::Run`), never from the host input thread. The per-frame order inside `CLevel::Update` (0x1793a1c) is: object/component updates (incl. `PlayerComponent::Update`), camera, then `Hud::Update` (0x16100a4) last. `Hud::Update` clears the button press/release edges at its start, so edges set any time before the next `CLevel::Update` are consumed once by the player, then cleared. (C)

## 1. Camera look

Touch path: `FullScreenRotateJoystick` (0x189a838 touchMoved) raises `EvStickMove` (id 8: `+12` float dx, `+16` float dy, both pixel delta / `Application::m_crtDPI`; `+20/+22` shorts x,y; `+24` byte flag). `CPlayerControl::onEvent` (`_ZN14CPlayerControl7onEventEPK6IEventPK12EventManager`, 0x138430c) turns it into yaw/pitch with a quadratic acceleration `(aimFactor + 2|dx|) * dx * CPlayerControl.cfg[+16] * CGameSettings::GetSensitivity()`, an ADS factor (`this+16`, `this+20`), and `CLevel+640` (time scale). Results go into accumulators `CPlayerControl+48` (yaw) and `+52` (pitch). (C)

`CPlayerControl::UpdateFromInput(CPlayerControl*, int dt)` (`_ZN14CPlayerControl15UpdateFromInputEi`, 0x1384e78, PLT 0x8d0860) then smooths them: a 10-sample history, decay 0.5 (0.85 if `CGameSettings+44`), writing `+56` yaw delta and `+60` pitch delta (degrees), `+64/+68` held values; accumulators are zeroed. (C)

`PlayerComponent::UpdateFromInput` (0x1815664) calls it on the embedded control at `PlayerComponent+32` and reads the results as `PlayerComponent+88/+92`. Yaw goes to `PlayerComponent::RotateYaw(float deg)` (0x18140a0); pitch becomes `SetPitch(current + d)` (0x180e1dc), clamped to a data-driven limit; pitch is a `SecuredValue<float>` at `PlayerComponent+2000`. Both are degrees. (C)

Recommended hook: post-hook `CPlayerControl::UpdateFromInput`; when `this == (char*)CLevel::GetPlayerComponent(CLevel::m_instance) + 32`, overwrite `*(float*)(this+56)=yawDeg`, `+60=pitchDeg` (and `+64/+68` the same). This bypasses smoothing, acceleration and sensitivity, keeps the pitch clamp, and also covers mounted-weapon use (a second caller). Convert counts with your own sensitivity, scaled by `curFov/baseFov` while ADS. Sign (I): the touch path gives `yaw = -k*dx` (drag right = negative `RotateYaw`) and `pitch = -k*dy` (`+k*dy` if `CGameSettings+46` invert); calibrate once at run time. In sniper scope or cinematics the engine calls `CPlayerControl::ResetControl` (0x1384918) and ignores look. Aim assist (`UpdateTargetRay`, see implementation notes) sits in the weapon ray code, independent of the raw look.

Why the view recentred (C by decompilation, run not reached): the injected deltas were not the problem; the game has a pitch auto-centre of its own. `PlayerComponent::UpdateAutoLeveling(int dt)` (0x18106a0, called from `PlayerComponent::Update` in every state) runs when `CGameSettings+20` ("auto leveling", default 1, persisted in settings.dat, a touch-options toggle) is set and the player is not in iron sight. Its timer `PlayerComponent+276` is reset by movement (`UpdateMovement`, stick velocity non-zero) and by `UpdateLookAt`, not by look input; once it passes the template threshold the pitch is eased toward a captured level (`PlayerComponent+792`) at a template rate in degrees per second through `RotatePitch`, which also zeroes the pending pitch delta (`PlayerComponent+92`). So standing still and looking around with the mouse made the view slide back to level after a moment: "recentres sometimes". The run log of the launch confirms the setting was 1 at boot ("auto level 1: forced off"). Fix: `CGameSettings+20` is forced to 0 every frame with the other mobile assists and `UpdateAutoLeveling` is replaced by a no-op. Other writers of pitch / yaw that move the view by design: scripted `UpdateLookAt` (tutorial / cinematic look-at targets), `UpdateResetPitch` (state 4 only), cover and parkour transitions, `PlayerComponent::ChangeWeapon` (`SetPitch(0)` in some swap paths), recoil (`UpdateWeaponRecoil`, additive per frame, not a recentre).

Fire path and the "shots go sideways" report (C by decompilation, fix not run): the shot direction is not a separate orientation. `CWeaponComponent::DoFire` (0x140ce14) refreshes the player node and the active `CCustomCameraSceneNode` (`UpdateTarget`), then `GetCorrectedEndPosWithSpread` / `GetEndPosWithSpread` (0x14106e8) builds the ray with `CLevel::GetRayFromScreenCoordinates` through the crosshair pixel (`CWeaponManager::GetCrosshairPosition`: `CWeaponManager+264/+268`, the configured displacement `m_pDefaultWeaponManager+168/+172` percent of `g_ScreenW/H`, plus the auto-aim magnet only while `CLevel::GetAutoAim`, which is replaced by 0) plus a random pixel offset: `x` and `y` are each `random(2r) - r` times `((g_ScreenW/1136 + g_ScreenH/640) / 2)`, with `r` = `CWeaponComponent::GetConeRadius` (float at `CWeaponComponent+848`). The camera is a child of the player node, so yaw / pitch, camera and ray share the same two values the injected look writes; no stale second orientation exists.

Cone radius model: `PlayerComponent::UpdateWeaponConeRadius` (0x1812d84, end of `PlayerComponent::UpdateFromInput`) calls `CWeaponComponent::UpdateConeRadius` (0x140ad20), which eases `+848` toward a target (standing radius, blended to the moving radius by run speed, the max radius while airborne, scaled for ADS) at `GetConeAdjustmentSpeed` per ms, and drives the HUD crosshair spread from it. Each shot adds `IncreaseConeRadiusShot`. The turn term: both `PlayerComponent::UpdateFromInput` (0x1815a2c) and `UpdateFromInputMountedWeapon` call `CWeaponComponent::UpdateConeRadiusTurn(this, turn, crouched, ads)` (0x140abac) every update with `turn = sqrt(dYaw^2 + dPitch^2)` in radians turned during that update (the `PlayerComponent+1224/+1228` values); it does `cone += (int)GetConeIncTurn() * turn`, clamped to `GetConeRadiusMax` (scaled for ADS). `GetConeIncTurn` is the weapon's armory param 0xEBCBC0D1, reduced by armor and multiplied by the player accuracy tuning factor. A touch drag turns slowly and the cone decays back between updates; a mouse flick turns hundreds of degrees per second, so the cone sits at its maximum while looking around and rays scatter over a wide square (probable cause of "bullets don't go straight"; not reproduced).

Fix (nova.ini `[game]` `turn_spread`, default 0): `UpdateConeRadiusTurn` is replaced by a no-op (both callers go through it), so turning adds no spread; base spread (standing / moving / airborne), ADS scaling, per-shot growth and armor effects are untouched. `turn_spread = 1` leaves the original function in place.

Crosshair displacement (finding, no change made): `CWeaponManager::UpdateHudData` (0x1415b48) takes the displacement in screen pixels, stores it at `+264/+268`, passes the same pixel values to the Flash crosshair (`Hud::SetCrosshairDeltaDisplacement`, `setDelta`), and, when nonzero, computes the angle between the displaced ray and the centre ray and feeds `PlayerComponent::SetCrosshairAngleCorrection` (the arms / weapon are rotated by it in `UpdateArmsCrosshairAdjustment`). So ray and arm correction use the same displaced pixel; only the Flash drawing may differ (stage units scaled by the non-uniform `GetScaleX/Y`), and only if the displacement is nonzero. The default weapon manager constructor zeroes the fields and the value comes from data; the layer logs it once (`[pc] crosshair displacement`) so a gameplay log shows whether this matters. The displacement is unmeasured, so it is left alone.

Player/camera access: `CLevel::m_instance` (data 0x2c76a20; `*(CLevel::m_instance+776)` is the player `CGameObject`); `CLevel::GetPlayerComponent(CLevel*)` (`_ZN6CLevel18GetPlayerComponentEv`, 0x1792090) returns the `PlayerComponent*` (component hash 480387101; handles MP). `CLevel::GetPlayer` is `_ZNK6CLevel9GetPlayerEv` (0x17932a4). (C)

## 2. Movement and actions

All HUD controls are Flash elements. Each Flash button calls a `Native*ButtonUpdate` which calls `Hud::SetButtonState(Hud*, int id, bool down)` (`_ZN3Hud14SetButtonStateEib`, 0x16192f8). `Hud::s_Instance` is data 0x2b13e38. Each element is 104 bytes at `*(Hud+240)`: `+0` pressed edge, `+1` released edge, `+2` held, `+3` enabled. Calling `SetButtonState` is exactly what touch does; no visibility check. (C)

Move: `Hud::SetMoveSpeed(Hud*, float strafe, float forward)` (0x1617f68) writes `Hud+40/+44`, range [-1,1], forward = +1; `PlayerComponent::UpdateMovement` (0x180a6a8) reads them every frame, normalising above length 1. Persistent, set per frame. (C)

Pick-up swap: `CLevel::StartSwapWeapon` (0x179b354). There is no jump button (parkour/cover jump is contextual, via interact). Fallback: none needed.

## 3. FOV and aspect

The projection is the stock glitch/Irrlicht perspective: vertical FOV in radians plus aspect. `CGameCameraComponent::SetCameraFov(float)` (0x13afc2c) clamps via `GameFOV::TranslateFovRad` (0x18979ac, [1 deg, 180 deg]) and calls the camera interface virtual +696 (`setFOV`, writes camera `+396`). `Application::RenderMainScreen` (0x177ff88) sets `g_ScreenW/H` from the viewport rect and calls the active camera's virtual +688 (`setAspectRatio`) with `w/h` every frame. Base FOV: `GameFOV::DESIGN_FOV` (data 0x285f3cc, 55 deg, loaded from the camera component template in `CGameCameraComponent::Load` 0x13afa08), `DEFAULT_FOV` (0x2ea46f0). `FOVs.xml` (`aspectratio`, `vfov` pairs, `DeviceOptions::LoadFovsTable` 0x178f250) is loaded but I found no consumer. `CCustomCameraSceneNode::setFOV` (0x1514f34) only derives a LOD scale from the ratio to `DEFAULT_FOV`. (C for the data flow; vertical convention I, from the `vfov` key and the helper below)

Consequence: with a vertical FOV fixed and aspect fed per frame, wider windows are already Hor+. No FOV hook is needed; just make `g_ScreenW/H` and the viewport the real window size. If a user FOV slider is wanted, wrap `SetCameraFov` (scale the vertical FOV). `GameFOV::HorizontalToVerticalFOV` (0x18979d0) and `VerticalToHorizontalFOV` (0x1897a3c) convert using `g_ScreenW/H` (C). Verify once: read the camera `+396` and compare the visible frustum at 16:9 vs 21:9 (I).

`g_ScreenW/H` (data 0x285f3c4/0x285f3c8) are written in `Application::Init` as `max(w,h), min(w,h)` (landscape forced), `OnAddScreen` (0x1786f24), `OnRemoveScreen`, and `RenderMainScreen`; world-to-screen, crosshair, hit-test and marker code read them live (C).

2D UI: `Application::GetScaleX/GetScaleY` (0x17863d8/0x178641c) are `max(w,h)/480` and `min(w,h)/320`: a 3:2 design base with non-uniform scale. The Flash HUD is set up in `MenuManager::LoadSWF` (0x1630f18)/`MenuManager::Draw` (0x1649ab4) with viewport `(0,0,g_ScreenW,g_ScreenH)` for full-screen layers, otherwise a 960x640 virtual size. There is no safe-area or notch code. At 21:9/32:9 expect HUD anchored to stage edges and possibly stretched on X (I, not run). Remedy if needed: hook the gameswf viewport call `sub_1C0902C` (0x1c0902c, args x,y,w,h,mode) to a centred 16:9 or 3:2 rectangle for the HUD layer only. `interface_<w>x<h>.bin` (`Application::LoadInterfaceData`, 0x1783590) is for the old native controls, which are hidden anyway.

## 4. Render resolution and quality tier

Size = guest window/surface size: `Application::Init` reads it from the glitch device. Scaling is `DeviceOptions::LoadProfile` (0x178c3c0): float `DeviceOptions::RTTInfo` (data 0x2c64a38) scales the main RTT (`MakeMultipleOf(4, RTTInfo*g_Screen*)` into 0x2c64a3c); the second scale `0x2c64a44` drives post-effect RTTs. Both come from a per-GPU-name, per-width `SScaleInfo` map; if the GPU name is unmatched they stay at their (uninitialised) defaults, so write both to 1.0f after `LoadProfile` (C for the mechanism; defaults I). Profile `ScreenScale` (`DeviceOptions+236`, default 1.0) is read in `ReadGameOptions` (0x178c9dc).

Tier selection: `GetGpuProfileName()` (0x178bf90) matches `DeviceOptions::m_gpuName` (the GL_RENDERER string; `GPUs.xml`) against thresholds on `max(w,h)` and returns `GPU_<n>.xml`; unmatched falls back to `GPU_5.xml`, the only tier file in the data set (I: presumably the top tier). `LoadCustomProfile` (0x178c6ac) then layers `<gpu>_<w>x<h>.xml`. Keys read by `ReadGameOptions`: `Max_FPS` (default 30), `AntiAliasing`, shadow/LOD/post-effect flags. Cleanest: keep the fallback by reporting an unknown GL_RENDERER; to force more, override the parsed fields after `ReadGameOptions` returns. `DeviceOptions::SetFakeDeviceSpecs` is a stub.

## 5. Frame rate and timing

Cap: `Application::LimitFps` (`_ZN11Application8LimitFpsEv`, 0x1785e70, called from `Application::Update` 0x1785d48 after `UpdateApp`) sleeps `1000/fps` ms with `fps = *(DeviceOptions::Singleton+156)` (`Max_FPS`, default 30). Hook: return immediately (it only refreshes `Application+1536`), or write 1000 to `DeviceOptions+156` after `LoadProfile`. Per-state `Application::SetTargetFPS` (0x177f23c) writes `Application+1224/1228`, not read by `LimitFps`. Present/vsync is the host's `eglSwapBuffers`. (C)

Delta time: `Application::UpdateFrameTime` (0x17814f0), per frame from `UpdateApp`, builds an integer-millisecond dt: a trimmed mean of 11 samples averaged with the latest, floored and clamped to [0,100], stored at `Application+1484`, cumulative `+1476`. `CLevel::Update`, `PlayerComponent`, `CPhysicsManager::Update` (0x175a1a8, max sub-step 1/60) and the SWF all use it. Gameplay is dt-driven, not frame-counted, but flooring biases speed: at 144 fps (6.94 ms) dt becomes 6, so the game runs about 14% slow; at over 500 fps dt is 0. Hook: post-hook `UpdateFrameTime` and rewrite `Application+1484` from a host fractional-ms accumulator (carry the remainder), or cap near 120 or 240 fps (C). `GS_InGame::CheckAndHandleTimeHack` (0x142eaa0) is an anti-cheat check on wall time; keep clocks honest.

## 6. Hiding the touch HUD

Elements live in a static id-to-SWF table (73 entries at 0x2785798, built in `Hud::Init`). Touch controls: fire 6, ADS 7, boost 8, grenade 16, grab 19, interact 21, exit 22, melee 48, medkit 55, repair 63, bullet 66, drone 37, revive/energy cells 39, weapon customize 40, reload/selector 0, pause 9, skip 17, move thumbstick 82/59, look thumbstick 60, container `actionContollersContainer` 72, item selector 38, heating 73. Keep: crosshair/ammo (2, 13), lifebar (53/54), minimap (46/61), objectives (25), messages, timers.

Hook `Hud::ShowElement(Hud*, int id, bool)` (0x160ea78): for ids above call `Hud::HideElement(Hud*, id, true)` (0x160a740, sets `+8`=1,`+9`=0) instead; also issue `HideElement` once after `Hud::Init` and `Hud::ReInit`. `HideElement` on 82/60 zeroes `Hud+40..52`, so write the move vector afterward. Button state still works while hidden (C). `Hud::EnterNoControlMode` (0x161989c) and `HideAllElements` (0x16159cc) hide everything; too broad. The native `ControlScheme7` (`_ZN14ControlScheme7C1Ev`, 0x1899634) only owns the full-screen look joystick; with no touches injected in game it is inert. Resulting visuals (I, not run).

## 7. Pause, back, settings

Pause: `CLevel::OpenIngameMenu(CLevel*)` (`_ZN6CLevel14OpenIngameMenuEv`, 0x17991f0), guarded by `CLevel::CanOpenIngameMenu` (`_ZNK6CLevel17CanOpenIngameMenuEv`, 0x1799280) and `Application::IsInActionPhase` (0x1786b60), single-player only. Or feed `NativeOnKeyAction(4,true)` (0x1e39388; Esc = BACK): it raises glf key 52, and `Application::OnEvent` (0x1786460, case 0xCD) opens the menu unless popups, tutorials or the player's death interfere, or closes popups first. MENU (82/103) behaves the same. Menus are Flash and need touches: forward the mouse via `OnGameTouchEvent(0,x,y,id)` (0x1e392e4) only while a menu is active (`MenuManager::IsMenuActive`, 0x1633114). (C; closing the pause menu with Esc is I.)

Settings: `CGameSettings::Singleton` (data 0x2ea45e0, a pointer): `+19` auto-sprint, `+24` sticky cover, `+44` look smoothing, `+46` invert Y, `+48/+52` sensitivity min/max, `+56` slider 0..1 (`GetSensitivity` 0x1891c9c = min+(max-min)*slider), `+60` gyro slider, `+72/+76/+80` ADS min/max/slider (`GetAimSensitivity`). Persisted by `CGameSettings::Save/Load` (0x189169c/0x1891960). Direct writes are safe. With raw look injection only `+46` matters; apply invert in your own code.

## 8. Campaign energy (stamina)

Model (C): `PlayerProfile` (via `s_MyPlayerProfilePtr`, data 0x28900f8) holds `SecuredValue<int>` current `+8648`, max `+8672` (`PlayerProfile::Reset` 0x1260350 sets 10; saved as `max_energy`), hard cap `+8696` (20), refill timestamp `+8720` (all encrypted). Regeneration: `PlayerProfile::CollapseEnergy` (0x1261e90) adds one unit per `CTuningManager::Singleton+2512` seconds (`REFRESH_ENERGY`, default 600, read by `CTuningManager::LoadGlobalConfigurationFromJSON` 0x127d4e8 from the server/CRM JSON, or the binary `LoadGlobalConfig` 0x1282aa0). Max rises by 5 with the extender consumable (hash 0x23BAD1F2). Per-mission cost: `RewardsData::TLevelInfo::GetEnergyCost` (0x13d49c4), `TLevelInfo+168`, overridden by `CShopManager::FindMissionInfo(hash)+224` when positive.

Gates: `onStartSpecificMap` (0x157b4c4) and `onBlackMisisonStart` (0x15a477c): `if IsEnergyUseActive { if !IsVersionPremium && cost > GetCurrentEnergy -> showNEEPopup() [blocked]; else DecCurrentEnergy(cost) }`. `onRestartMission` (0x15b7298): blocked unless `IsVersionPremium || cost <= GetCurrentEnergy`, then `DecCurrentEnergy`. `PlayerProfile::DecCurrentEnergy` (0x1262480) is a no-op when `IsEnergyUseActive` is false.

Recommended hooks (do all three, all `ret`-style):
1. `PlayerProfile::IsEnergyUseActive` (`_ZNK13PlayerProfile17IsEnergyUseActiveEv`, 0x1262594) returns 0: skips the check and the deduction; the top bar's `extender` flag (`!IsEnergyUseActive`, `onAskForTopBarData` 0x159e4a0) then reports unlimited (I for the visuals).
2. `RewardsData::TLevelInfo::GetEnergyCost` (0x13d49c4) returns 0: closes the `onRestartMission` path and shows no price.
3. `PlayerProfile::IsTLEEnergyUseActive` (0x126270c) returns 0 for the event-mode energy (`DecCurrentTLEEnergy` in `CLevel::GameplayStart`, `onMatchmakingStart`).

Alternative single hook: `ApplicationInfo::IsVersionPremium` (0x188bcf4, a stub returning 0) to 1, which drives (1), (3) and the restart gate, but also hides ads, IAP and rate popups and changes `NativeIsPremium` and the controls menu: broader, I would not take it. Not energy: "energy cells" (`Hud::SetEnergyCellsCount`, `PlayerComponent::CallEnergyCellFn`) are in-mission revive items. A dev cheat `InfiniteEnergy` exists in `AutomationInterface::OnEvent` (0x143e348), not chased.

Other single-player gates seen, not chased: Black Market refresh timer (`PlayerProfile::GetBlackMarketRemainingTime`, 0x1274658); black-mission timed window (`GetBlackMissionRemainingTime`, 0x1263c10, `CTuningManager+2584`); spin-wheel cooldown (`CTuningManager::GetSpinWheelRewardRemainingTime`, 0x1294884); daily login/task claims (`DailyTask::Manager::ClaimDailyTaskReward`, 0x13c1fd8); timed consumable effects (`Inventory::GetConsumableEffectRemainingTime` 0x125e314, `IsConsumableEffectActive` 0x1257e34, e.g. VIP pass 0x130ADFF9); interstitial/reward ads (`GameGLAdsManager::ShouldWaitForInterstitial`, 0x16c6b5c); the server clock behind all of them (`SafeTimer::GetAppTime` 0x1892b90).

## Implementation notes (src/pc, confirmed by one scripted run unless marked)

Hook mechanism (`pc/hook.cpp`): `Wrap(fn)` copies the first 4 instructions of the target into a trampoline in the Thunks zone (followed by `ldr x16 / br x16` to fn+16) and patches the entry with `hle::HookGuestFunction`; the HLE handler calls the trampoline with `CallPacked` (`CallOriginal`) and runs host code before/after. This covers PLT/GOT, direct and virtual callers at once, which a `bl` call-site patch would not (the Thunks zone is out of `bl` range of the library). Wrap refuses prologues with adr/adrp/b/bl/b.cond/cbz/tbz/ldr-literal in the first 4 instructions; none of the hooked functions has one. A handler of a `void` function must read `this` (x0) before calling the original: x0 is garbage afterwards (a `Hud::ReInit` hook that did not crashed the first run).

- Look (item 1, C): hooked `CPlayerControl::UpdateFromInput` (3 callers: normal, mounted weapon, cinematic). Signs match the touch path: mouse right = yaw -= dx*s (turns right), mouse up = pitch -= dy*s (looks up); both confirmed on screen. `PlayerComponent+2532` (cinematic) and `+365` (frozen) set = look ignored; `+1785` = in iron sight (ADS scale). The pitch clamp still applies (a 300 count flick up moved the view less than the sensitivity predicts in the tutorial room).
- Gameplay predicate (C): `Application::IsInActionPhase(app)` (current state is GS_InGame and `CLevel+176 != 1`) and not `MenuManager::IsMenuActive(menumgr, -1)` and `CLevel+776 != 0`. The pause menu is a pushed GS_InGameMenu state, so it flips to "menu"; tutorial popups ("Skip tutorial / Continue") are MenuManager menus and flip it too. Evaluated every frame in the `UpdateFrameTime` hook and published to the host thread.
- Buttons (C): `Hud::SetButtonState` called after `Hud::Update` on the game thread. Taps = down + up in one frame (edges are consumed by the next player update, then cleared). ADS (7) toggles on the press edge: hold-to-aim presses on key down and again on key up when `PlayerComponent+1785` says it is still on. Sprint (5) makes the engine run forward whenever it is held, so it is only pressed together with forward. Weapon 1-4: write the slot to `PlayerComponent+1836` (what `UpdateChangeWeapon` does) after checking `CWeaponManager+416` (slot -> weapon vector, -1 empty) and `+392` (24 byte weapon entries); wheel: `Hud::ChangeWeapon(+-1)` once per frame.
- Touch HUD (item 6, C/visual): hidden ids 0 6 7 8 9 16 37 38 40 48 55 59 60 66 72 82 through the `ShowElement` wrapper plus `HideElement` after `Hud::Init` / `ReInit`. Kept on purpose: contextual prompts 17 19 21 22 39 63, gauges, crosshair, life, objectives. Screenshot of the first mission shows crosshair, life bar and the consumable icons, no stick, pause or fire buttons.
- Frame time (item 5, C): `Application::UpdateFrameTime(this, prev_ms, now_ms)` (it is `(int,int)`, not `()`), dt at `+1484`, running total `+1476`, newest history sample `+1528`. The post hook replaces dt with whole milliseconds from a host fractional accumulator (QPC) and fixes the total and the history slot. Run log: over 600 frames at ~135 fps the engine's own value summed to 97.4% of real time (about 2.6% slow), the replacement to 100.0%. When the engine's own delta is more than 3 ms below the wall clock (it reset its timestamps after a state change) its value is kept. `Application::LimitFps` is replaced by a no-op.
- Render scale (item 4): `DeviceOptions::LoadProfile` writes the scales and then derives the RTT sizes inside the same function, so a post hook sets `RTTInfo` (+0 main scale, +12 post scale) to 1.0 and recomputes the four sizes (`+4/+8`, `+16/+20`, width/height rounded up to a multiple of 4). `GL_RENDERER` is reported as "Adreno (TM) 650" by the gles HLE, which already selects the top tier profile.
- Energy (item 8): `IsEnergyUseActive`, `IsTLEEnergyUseActive`, `GetEnergyCost` replaced by `return 0`.
- Mobile assists (C by decompilation; boot-time forcing confirmed by the run log, gameplay effects not run, see below). The first four are fields of `CGameSettings` (pointer at `CGameSettings::Singleton`), set from the touch options menu, persisted in `settings.dat`, defaults on: `+12` int auto aim (`CLevel::GetAutoAim`, 0x179be48), `+16` auto fire (`CLevel::GetAutoShoot`, 0x179be7c), `+18` auto fire while aiming (read directly in `PlayerComponent::Update` / `UpdateFireData`), `+19` auto sprint (plus `+20` auto leveling, a fifth, see item 1). Auto fire: `UpdateFireData` hides the fire button and sets "IsFireButtonPressed" whenever the crosshair target is on sight; auto aim: `UpdateTargetRay` (0x1414d44; `UpdateAimAssist` is only a stub in front of it) offsets the crosshair / ray toward the target (`CWeaponManager+244/248`, magnetism coefficients of the weapon preset) and sets the aim friction `CLevel+640` that `CPlayerControl::onEvent` multiplies into the touch look (the raw mouse look bypasses it). Auto sprint: `PlayerComponent::CheckSwitchSprintMode` (0x180a3a0) sprints when `+19` is set, the sprint element is enabled and the stick is pushed forward (`PlayerComponent+1753/+1754`); with `+19 == 0` it needs Hud button 5 held (`IsButtonActive`), which is what the Shift key sends. Fix: all four fields are forced to 0 once per frame in the `UpdateFrameTime` hook (logs `mobile assists were ...: forced off` when it had to change something, which also covers settings.dat and the options menu), and `CLevel::GetAutoAim` / `GetAutoShoot` (they also honour the Lua `Player_AutoAim` / `Player_AutoShoot` overrides) are replaced by `return 0`. Not touched: sticky cover (`+24`), `Hud::CanUseSniperAbility` (a sniper ability that fires, `PlayerComponent+2690`).
- Aim down sights (C by decompilation; the run did not reach gameplay): the engine path is `PlayerComponent::EnterIronSight` (0x181cd38, sets `+1785`, `CSMExecutor "IsInIronSigh"`, `CWeaponComponent::SetAimed`, aim sensitivity), `ExitIronSight` (0x18190cc) and `CheckIronSight` (0x181a4ec, blends the camera FOV to the weapon's iron sight FOV, or back to the idle FOV, through `CGameCameraComponent::SetFovInterpolation(target_rad, ms)`). Touch reaches them through Hud button 7 in `PlayerComponent::UpdateIronSight` (0x1812a04), which returns early unless the weapon template has an iron sight interface (`CWeaponComponent::HasIronsightInterface`, template `+96`, scoped weapons only) and in states 2, 3, 4, 18, and which only calls `CheckIronSight` for weapon class 7 (sniper). That is why RMB did nothing: the old code only tapped button 7. The layer now calls Enter / Exit / CheckIronSight itself for every weapon (hold on RMB, or press to toggle with `aim_mode = toggle`; it only exits an aim it started itself), skipping the same states and cinematic / frozen. Iron sight FOV is `CWeaponComponent+892` (template `+84`, degrees; `+896` override), idle FOV template `+152` (`< 0` = `CGameCameraComponent+568`). A weapon whose iron sight FOV is not below 97% of its idle FOV gets `idle / ads_zoom` (nova.ini, default 1.4) through `SetFovInterpolation` directly. Look sensitivity while aiming = `sensitivity * tan(cameraFov/2) / tan(idleFov/2) * ads_sensitivity_scale` (default 1.0: same turn per degree of FOV as hip fire), with the live camera FOV read through `GetCameraFov` so it follows the blend. The log prints `sprint ON/off` and `aim ON/off` with the camera FOV (and once more after 120 frames) for checking.
- Key list (nova.ini `[keys]`, all rebindable; defaults): WASD move, mouse look, LMB fire (Hud 6, held), RMB aim (hold or toggle, `aim_mode`), R reload (0), Space jump (see below), F interact (21, 19, 22; Space no longer sends it), C or Left Ctrl crouch (see below, `crouch_mode` hold or toggle), Left Shift sprint (5, only with forward), G grenade (16), V or mouse4 melee (48), 1-4 weapon slot, wheel next / previous weapon, Esc pause / back, F12 screenshot, Alt+Enter fullscreen. Consumable slots: Q armor, E medkit, T ammo, X boost. Free cursor: hold Left Alt (`cursor_key` in `[input]`, any keyboard key or `none`).
- Free cursor (C by code, not run): while `cursor_key` is held `InGameplay()` (the host-thread predicate `main.cpp` uses to pick the input mode) reports false, so the existing menu mode applies: cursor shown (relative mouse mode off), clicks and drags are touches (`OnGameTouchEvent`), so any HUD icon, tutorial prompt or popup can be tapped. The game-thread hooks use `Playing()` instead (the real gameplay state), so WASD, the keys and the consumable keys keep working while the cursor is free. The key state is read from SDL's keyboard state (survives the `ReleaseAll` that runs on every mode change, reset by SDL on focus loss). Releasing the key recaptures the mouse; the accumulated counts are zeroed and motion is dropped for 50 ms, so the view does not jump. Alt+Enter is handled in `main.cpp` before the key reaches `OnKey`, independent of the mode.
- Consumable slots (C by decompilation, not run): the three in-mission consumables are Flash icons (`Hud` elements 75 shield, 39 energy cell, 79 ammo belt, each a `updateMultiSelector` clip) whose tap sends `SWF_COMMAND_USE_CONSUMABLE` to `Consumable_OnUse` (0x159c5d8), which hashes the item type and calls `onRestoreShield()` (0x159c294, kinetic armor: refills the shield, `Inventory::UseConsumable` 0xC20A7674, `PlayerComponent::CallArmorConsumedFn`, which is what the tutorial step "tap the Vanguard Armor icon" waits for), `onRestoreLife()` (0x159c0f8, energy cell = health to full, `CallEnergyCellFn`) or `onRestoreAmmo()` (0x159c454, `CWeaponManager::GiveAmmo`, `CallAmmoBeltConsumedFn`). Each checks the item count and that there is something to restore, so a key press with no item or full stats does nothing, exactly like the icon. The layer calls these three functions directly from the `Hud::Update` post hook (guest game thread). E first spends a picked-up medkit if `PlayerComponent+816 > 0` (Hud button 55 released edge, what the touch medkit icon does; Lua `Player_AddMedkit`), otherwise the energy cell. X is the weapon boost bonus button (Hud 8, pressed edge in `UpdateBoostBonus`, only for weapons with `HasBoostBonusButton`). The slot order is the code order (shield, energy cell, ammo in `SpRespawn` / `onResume`); the on-screen order of the icons is inside the SWF and was not checked. Old `ability1` / `ability2` keys in nova.ini are ignored.
- Jump (C by decompilation, not run): the engine has no jump input. `CCharacterController::Jump(this, speed, seconds)` (0x1756ae0) has no caller in libNOVA (only a dynsym export), `CBaseControlScheme::GetJumpControl` is a control-scheme virtual nobody reads for the player, `PlayerSetJumpLimit` / `PlayerSetJumpDamageFactor` are Lua stubs, so there is no level-script gate to lift. The controller is `**(CPhysicsManager::Singleton+328)`. `Jump` refuses unless `+212` (airborne) and `+215` (jumping) are both 0, which is the ground check; otherwise it stores `speed` at `+236` and `seconds` at `+232/+240`, and `Move` (dt in seconds, as `PlayerComponent::Update` passes it) applies the upward speed `speed * (remaining / seconds)^2` while the controller's gravity (acceleration vector at `+320..+328`, z up) pulls down; `+215` clears when gravity wins, `+212` is set and gravity accumulates until landing. `PlayerComponent::Update` maps `+212` to `SetState(1)` (air) every frame, so the falling states follow on their own. The layer solves `speed` numerically for an apex of `jump_height` (nova.ini, default 0.4) times the capsule height (`+224`), with `seconds` = 0.35 and the controller's own gravity (unit independent); one jump per Space press, only in free-movement actions (0-4, 13, 14, 20, 21), not in cover, on a mounted weapon, in a cinematic or frozen; Space while crouched stands up instead. Jump / land sounds are `CActorSoundsComponent::OnEvent` event 12 with payload `{53, 1 or 0}`, raised through `CGameObject::OnEvent(player object, 12, payload)` (audible only if the surface defines jump sounds). There is no jump animation in the code: the state machine only reacts to the airborne flag. Height and feel not verified in a run; the first gameplay log line `[pc] jump:` and `[pc] crosshair displacement ... controller capsule ... gravity z` print the numbers used.
- Crouch (C by decompilation, not run): Hud button 1 (`NativeCrouchButtonUpdate`) is read by nothing native and by none of the actor scripts I found, and `IsCrouchButtonEnabled` (`CGameSettings+23` inverted, default enabled) is not referenced by them either, so the crouch button is vestigial. The stance is only entered by `PlayerComponent::EnterCover` (flag `PlayerComponent+1786`, `CCharacterController::SetCrouched(true)` halving the capsule height, `sfx_crouch`, the additive "Crouch" / "Idle_Crouch" animation unless in iron sight) and left by `PlayerComponent::Stand` (flag, capsule, `sfx_stand`, blend out) or `ForceStand`. The flag also selects the crouch step sound set (event 47, stance 2) and walking speed in `PlayerComponent::Update`. The camera height is not touched by the code (`SetCurrentHeight` only in Init / weapon change / cinematic), so any lowering relies on the additive animation. A free-standing crouch therefore exists as a stance but not as an input: the layer reproduces the stance part of `EnterCover` (without the obstacle) on C / Left Ctrl (hold by default, `crouch_mode = toggle`), stands with `Stand`, drops it while sprint is held with forward, in the air, in special actions and on a jump, and re-applies it every frame (a cover exit that stands the player up is undone while the key is held). Not verified in a run: whether the view visibly lowers, and enemy reaction.
- Aim state is self-correcting (replaces the one-shot Enter / Exit): each gameplay frame compares the desired aim (RMB held, or the toggle) with `PlayerComponent+1785` and calls `EnterIronSight` / `ExitIronSight` until they match; the toggle is cleared on every mode switch and focus loss (`InputEpoch`, bumped by `ReleaseAll`) and when the game ends the aim itself. Probable cause of the stuck aim (by reading the old code and the weapon scripts, not reproduced): the old hold logic only exited an aim it had started (`ours`), and `AdsEnter` reported failure when the engine took the aim a frame late or through its own scripts (the weapon state machines call `Player_EnterIronSight` again after a reload / pump when `wasInIronSigh`), so a release while the game refused `ExitIronSight` (reload, swap), or an aim re-entered by a script, was never undone. A zoom the layer applied (`SetFovInterpolation`) is taken back when the game ends the aim itself.
- Auto leveling (`CGameSettings+20`) is a fifth mobile assist, forced off with the other four (see item 1).
- Turn spread (C by decompilation, not run): `CWeaponComponent::UpdateConeRadiusTurn` replaced by a no-op unless `turn_spread = 1` (see the fire path paragraph in item 1).
- Tutorial prompts that wait for a tap: not handled automatically. `Hud::IsAnyTutorialActive` is also true for hints that need the gameplay controls (move, shoot, crouch), so it is not a reliable "tap needed" state; popups that are MenuManager menus already switch to menu mode (gameplay predicate above). Hold Left Alt for the rest.
- The first campaign mission is the tutorial: on a fresh profile it shows "Skip tutorial / Continue" and the tutorial steps wait for touch gestures, so skip it once.
